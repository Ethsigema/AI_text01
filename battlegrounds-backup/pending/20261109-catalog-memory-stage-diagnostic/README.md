## 1. 预载阶段提前暴露阻塞

先设置单Godot、2 CPUs、180秒、每25ms采样、RSS 1.4GiB提前停止、系统余量640MiB停止、地址空间3.5GiB上限；启动时要求至少2100MiB MemAvailable。本次启动时可用约2.08GiB。按当前catalog中849个顶层const preload的声明顺序逐项加载并保留引用，逐项记录引擎活跃/峰值内存。另一个函数内preload未列入顶层列表，故全文件调用数仍为850。

完成前848项后，进入 combat.gd 的预载。35.31秒时进程收到SIGKILL，maxrss为982772KiB（约959.7MiB）；最后阶段采样系统MemAvailable最低1,334,935,552 bytes。控制器记录process_exit，不是RSS/余量/时限保护触发。该值明显低于计划RSS阈值，也低于历史约2.7GiB的失败峰值。

因此，历史失败峰值不能作为当前安全容量保证。缺少内核/cgroup终止事件，不能断言OOM、固定容器限额或平台终止原因。没有提高阈值重试，也没有调用完整load_catalog或Game。完整catalog脚本加载及实例化的后续标记均未到达。

可证实的预载成本：
- native_spell_listener_stock.gd对应步骤使引擎活跃内存增加217,188,168 bytes（约207MiB），耗时12.72秒；这是该入口新增递归依赖的总成本，不是单个脚本本体。
- harbinger_eot_admission.gd对应步骤增加87,259,353 bytes（约83MiB），耗时4.59秒。
- combat预载前，引擎活跃内存491,720,772 bytes，历史峰值769,639,788 bytes。
- 引擎记账内存不等于进程RSS，也不能将各步骤增量与历史完整Game峰值相加。

## 2. 小探针：更严格512MiB RSS上限

外部终止后，后续只运行独立小探针，512MiB RSS停止、640MiB系统余量、45秒、单Godot，不再次预载整个依赖图。

原始30,883,879-byte目录文件的哈希：
- 原文本解码+SHA：最大RSS193976KiB。
- 字节流SHA：最大RSS59852KiB。
- 当前有效UTF-8文件两者摘要一致，但实际Godot对照证明BOM、非法UTF-8、NUL和缺失文件的结果不同。因此不能直接替换文本哈希来省内存，本轮没有这样修改工程。

短函数作用域探针：
- 内联和短函数的两个真实目录文件摘要、七种编码/缺失文件用例摘要一致。
- 短函数返回后，原始文本缓冲不再留在调用方活跃内存中；但RSS峰值194156→194144KiB，实质未降。
- 内联版本在下一次文本哈希后也会释放上一大缓冲，并非每条哈希语句都永久叠加。不能据此声称已经找到完整加载的全部增长原因。
- 此方案没有证明峰值收益，未封成运行源码修复。

SMALL_PLAN是共享资源上限配置，其中sequence文字沿用了最初的原始文件哈希描述；各实际gate范围和继承字段解释见SCOPE_RECONCILIATION.json。执行脚本、哈希和原日志均保留，没有更改历史执行记录。

## 3. 静态依赖图与下一步候选

当前catalog静态preload图可达1538个脚本、36,493,976源码bytes；这不是内存大小，文本图也不覆盖运行期load或证明缓存复用。DEPENDENCY_GRAPH.json给出全部路径、哈希、边和循环。

有两个值得独立设计的耦合边：
1. native_spell_listener_stock.gd第8行引入spell_cast_listeners.gd，仅为了第28行完整来源校验。该入口经此边独占可达829脚本、21,329,705源码bytes。
2. harbinger_eot_admission.gd第4行引入end_turn_repeats.gd，仅为了第48–55行身份/类型识别；该边独占可达174脚本、5,813,524源码bytes。

可考虑抽取完整纯校验/身份识别为共享叶模块，原宿主保留兼容委托。必须保留全部修订、配对、来源hash、未知family拒绝、错误文字与顺序，不能只做宽泛ID判断或绕开附件校验。未实施上述结构改动。

其他入口仍会加载原宿主，所以抽取仅可能改变解析重叠与入口耦合，不保证完整图最终驻留下降。最安全下一步是先完成叶模块接口及逐输入等价测试设计，在稳定、可观测的资源条件下再测完整加载；当前不抬高阈值硬跑。
